# kestrel-bridge

Sidecar that lets the Kestrel phone app (identity **B**) read and send as the MeshChatX identity
**A** without running A on the phone. It has its own identity **S**, talks to MeshChatX over its
authenticated HTTP + WebSocket API, and serves B over an RNS Link (online) or LXMF (offline / LoRa).

Protocol: [`docs/bridge-protocol.md`](../docs/bridge-protocol.md) (`protocol_version` 1).

```
phone B --(RNS Link / LXMF)--> S (this sidecar) --(HTTP + WS)--> MeshChatX (A)
                                  \--(RNS, TCP client)--> MeshChatX's Reticulum (transport node)
```

## RNS modes

| | `standalone` (default, recommended) | `shared` |
|---|---|---|
| Reticulum | the bridge starts **its own** instance (`share_instance = No`, not a transport node) with one `TCPClientInterface` to MeshChatX | attaches to MeshChatX's shared instance |
| RNS config | generated by the bridge at every start from `[rns]` (no hand-written config) | minimal config, written only if missing |
| Network | own container on the Docker network MeshChatX uses; MeshChatX reached by DNS name (`meshchatx`) | shares MeshChatX's network namespace (`network_mode: service:meshchatx`) |
| MeshChatX recreated (image auto-update) | **survives by itself**: RNS reconnects the TCP interface, the HTTP client logs in again, the bridge re-announces. No watchdog, no manual recreate | the bridge is stuck in a dead network namespace and must be force-recreated |
| Push profile | from the phone's own Link (RTT / MTU) | from the shared instance's path table (needs `rpc_key`) |
| Example | [`deploy/docker-compose.example.yml`](deploy/docker-compose.example.yml) | [`deploy/docker-compose.shared.example.yml`](deploy/docker-compose.shared.example.yml) |

**Use standalone** unless you have a reason not to. In standalone mode MeshChatX's Reticulum must
expose a `TCPServerInterface` (for example `listen_ip = 0.0.0.0`, `listen_port = 4242`) that is
reachable from the bridge container *over the Docker network only* (do not publish that port for the
bridge's sake). MeshChatX's RNS acts as the transport node: the bridge announces `kestrel.bridge`
through it, and the phone finds a path via the same node.

> **Upgrading from an earlier version:** the default mode changed from shared to standalone. An
> existing shared-mode setup must add `mode = "shared"` under `[rns]` (or be moved to standalone).

## Setup (standalone)

1. **MeshChatX side:** make sure its Reticulum config has a `TCPServerInterface` reachable on the
   Docker network (e.g. port 4242), and note the Docker network MeshChatX is attached to.
2. **Compose:** add the service from [`deploy/docker-compose.example.yml`](deploy/docker-compose.example.yml)
   and point its `meshchatx-net` entry at your MeshChatX network (`external: true`). The service has
   `restart: unless-stopped` and no `network_mode`; no port is published.
3. **Config:** copy [`config.example.toml`](config.example.toml) to `kestrel/config/bridge.toml`
   and edit it. Check it (no secrets are printed):
   `docker compose run --rm kestrel-bridge python -m kestrel_bridge --check-config`.
4. **Password:** MeshChatX has a single web password and no API tokens, so the bridge needs that
   password. Put it in a file (mode 600, owner uid 10001) mounted read-only and set
   `meshchatx.password_file`. It is never logged. The bridge never calls `/auth/logout` (that would
   log the human out of MeshChatX as well); on a 401 it logs in again, with exponential backoff.
   If you change the MeshChatX password, update the file and restart the bridge.
5. **Identity S and its address:** on first start the bridge creates `storage/identity`. Print the
   address data the phone needs:
   `docker compose run --rm kestrel-bridge python -m kestrel_bridge --print-address`
   (destination hash of `kestrel.bridge`, the `lxmf.delivery` hash and the public key of S).
6. **Authorize a phone (add B's public key):** in the app, copy B's **full public key** (128 hex
   characters, not the 32-character address) and add it to `[whitelist] phone_public_keys` in
   `bridge.toml`, then `docker compose restart kestrel-bridge`. Only identities in this list can
   use the bridge, on both transports.
7. **Start:** `docker compose up -d kestrel-bridge`. Watch `docker compose logs -f kestrel-bridge`.
   INFO logs never contain message text or secrets.

### `[rns]` configuration

```toml
[rns]
mode = "standalone"            # or "shared"
tcp_host = "meshchatx"         # standalone: MeshChatX's TCPServerInterface (default "meshchatx")
tcp_port = 4242                # standalone (default 4242)
# ifac_name = "example-network"                          # standalone, optional
# ifac_passphrase_file = "/run/secrets/ifac_passphrase"  # standalone, optional; the passphrase is never inline
announce_interval = 1800       # seconds, default 30 min
```

* `meshchatx.base_url` is the MeshChatX HTTP/WS API, e.g. `http://meshchatx:8000` (Docker DNS on the
  shared network).
* `ifac_*` are only needed when MeshChatX's TCP interface uses an IFAC network name/passphrase. The
  passphrase is read from a file (mounted read-only) and written to the generated RNS config
  (mode 600) in `config_dir`; keep that directory private.
* `require_shared_instance` exists only for `mode = "shared"` (and must stay `true`); `tcp_*` and
  `ifac_*` are rejected in shared mode.

### Announces

`kestrel.bridge` is announced on startup, every `rns.announce_interval` seconds, and **after every
TCP reconnect** (a small thread inside the bridge watches the interface `online` flag), so the phone
can find a path through the MeshChatX transport node again after MeshChatX restarted and lost its
path table. In shared mode only the startup/periodic announces apply.

### Push profile (full vs constrained)

`push.profile = "auto" | "full" | "constrained"` (default `auto`). A phone's *effective* profile is
the most restrictive of this setting and the phone's own `/subscribe` hint (the hint can only
downgrade).

* `auto`, **standalone**: the bridge has no access to MeshChatX's path table, so it uses its own view
  of the phone's live Link: **`full` if RTT < `push.full_max_rtt` (default 1.5 s) and link MTU >=
  `push.full_min_link_mtu` (default 1000 bytes)**, otherwise `constrained`. LoRa/serial paths
  negotiate the 500-byte base MTU and have RTTs of seconds; TCP paths negotiate a large MTU. If the
  Link has no measurement, `push.unknown_profile` applies (default `constrained`).
* `auto`, **shared**: the next-hop interface of the phone in the shared instance's path table
  (`push.fast_interfaces` -> `full`), which needs the shared instance's `rpc_key` (see below).
* `full` / `constrained`: fixed, in either mode. No `rpc_key` is needed.

## Health

`python -m kestrel_bridge --healthcheck` reads the bridge's heartbeat (written every 15 s, also while
MeshChatX is unreachable) and prints what it sees:

| Output | Exit code | Meaning |
|---|---|---|
| `ok` | 0 | RNS interface online and MeshChatX reachable (WebSocket connected) |
| `degraded: MeshChatX unreachable` / `degraded: RNS interface offline` | 0 | the bridge runs and is reconnecting by itself; the container stays *healthy* so Docker does not flap while MeshChatX restarts |
| `unhealthy: no heartbeat` / `unhealthy: stale heartbeat` | 1 | the bridge process is stuck or not running |
| `degraded: ...` with `--strict` | 3 | for monitoring that wants to alert on degraded states |

While MeshChatX is down the bridge refuses commands with a retryable `upstream_unavailable` error
and resyncs (`resync` push event) when MeshChatX is back.

## Notes (shared mode)

- **`rpc_key` (optional, shared mode only).** Attaching to the shared instance and using
  destinations needs no key. Asking the shared instance which interface leads to the phone uses
  Reticulum's RPC, authenticated with the shared instance's `rpc_key`. Without a matching key the
  lookup fails and the bridge falls back to `push.unknown_profile`. To enable the full profile for
  TCP phones either set the same explicit `rpc_key = <hex>` in MeshChatX's Reticulum config and in
  the sidecar's `.reticulum/config`, set `push.profile = "full"`, or just use standalone mode. Do
  not commit or log this key.
- **MeshChatX recreated:** with `network_mode: service:meshchatx` the sidecar lives in MeshChatX's
  network namespace. After the MeshChatX container is *recreated* (image update) run
  `docker compose up -d --force-recreate kestrel-bridge`. A plain `docker restart meshchatx` is
  fine. This is the reason standalone mode exists.
- The bridge attaches with `require_shared_instance=True`; it never becomes the shared instance itself.

## Notes (all modes)

- **MeshChatX version:** checked against an allowlist (`meshchatx.allowed_versions`, default
  `4.12.*`, and `/app/info` `api_version`). On a mismatch the bridge keeps running, reports
  `compat.ok = false` in `/hello` and refuses commands with `upstream_incompatible` until a
  tested version is found (re-checked every 5 minutes).
- **MeshChatX restart:** the HTTP client survives a server that refuses connections for a while and
  then comes back with new sessions and CSRF tokens (it logs in again); the WebSocket layer
  reconnects with backoff and triggers a resync.
- **Start order:** the bridge does not wait for MeshChatX before starting Reticulum; commands fail
  with `upstream_unavailable` until MeshChatX is reachable and compatible.
- **Trust:** the bridge holds the full MeshChatX session power. It exposes only the commands in
  the protocol, and only to whitelisted public keys.

## Development

```
python -m venv .venv && .venv/bin/pip install -e .[dev]     # Windows: .venv\Scripts\pip
python -m unittest discover -s tests -t .                    # unit tests, no network/RNS needed at runtime
KESTREL_IT=1 python -m unittest tests.test_integration_rns  # Reticulum integration test (starts subprocesses)
```

`tests/fake_meshchatx.py` is a small fake MeshChatX (cookie + CSRF login, newest-first paging,
WebSocket) used by the unit and integration tests. The integration test runs the bridge in standalone
mode against a Python transport node with a TCPServerInterface (`tests/it_transport.py`), connects a
phone client to the same node, then restarts the node and checks that the bridge reconnects,
re-announces and the phone can call `/hello` again.
